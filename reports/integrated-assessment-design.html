4. Scoring categories and constructs

Each current source row has exactly one scoring category and one construct: Spiritual Gifts → one gift; APEST → one ministry approach; Strengths → one strength approach; Personality → one independent dimension. The map's scoring_link is the category/construct link. There are no shared questions or cross-category links in the current source. Do not invent shared scoring from semantic similarity. A future active-link filter can support multiple links by retaining only links whose section/construct/gift toggle is enabled, but this inventory must remain one link per row until a separately justified cross-scoring model exists.

  • APEST: builder, insight, connector, caregiver, teacher.
  • Spiritual Gifts: all 26 exact supported names in source order.
  • Strengths: all 18 exact approaches in source order.
  • Personality: Social Energy, Decision Lens, Planning Style, Focus Style, Action Style, Pace Preference, Work Style; each is scored from its own three prompts.

5. Questions that disappear when a section or construct is disabled

Current: APEST, Strengths, and Personality rows are filtered by their subsection toggles; disabled rows are unregistered and omitted from the submitted response map. Spiritual Gifts are filtered by church.enabledSpiritualGifts, and the Celibacy gift is additionally omitted when the family situation begins with “Married.” The whole section also gates whether the section appears and whether its payload is submitted. Integrated-flow rule: build the active question set before calculating progress, validation, navigation, or submission. A row with no active scoring link should disappear.

6. Rows retained when one scoring connection is disabled

Verified current state: there are no multi-link rows, so no current row has a second enabled scoring connection that can retain it. Every row is single-category in this bank. Future-compatible filter: represent each row as scoring_links[]; retain the row when at least one link is enabled, and submit/score only the active links. Never preserve a row solely because its wording resembles another construct. This directly avoids the request's cross-scoring example becoming an invented current behavior.

7. Spiritual Gift ON/OFF behavior

Current: individual gifts are selected by church configuration and validated server-side; enabled gift names must be supported, distinct, and at least three when explicit. Gift question count is 1–4, default 3. Current creation filters gift responses to the active gift set and stores the entire validated assessment configuration as assessmentConfigurationSnapshot. The current client reinitializes gift response state when the active gift configuration key changes and filters Celibacy for married participants.

Proposed: in the integrated pilot, a disabled gift removes gift-only active rows, stops that gift's scoring/result display/PartFinder signal for the new attempt, and never deletes historical answers or rewrites historical profiles. A mixed row would remain only if it had another active scoring link; the current inventory has none. Gift toggles must be frozen into the attempt snapshot at start, not re-read mid-attempt.

8. Progress calculation

Proposed: one integrated progress value: answeredActiveQuestionCount / activeQuestionCount × 100, rounded for display. The denominator is the frozen active question set for the church, adult pathway, participant-specific conditions, section/subsection toggles, enabled gifts, count settings, and special-subsection policy. Disabled rows never count. “Answered” means a valid response in the active set; the future N/A value is valid but unscored. Show one label such as “Assessment progress: 45%,” not four category percentages. The current UI instead shows “Step n of n” and per-section answered counts, so this is not current behavior.

9. Save/resume when configuration changes after start

Verified gap: the current adult page has no draft save/resume implementation. React Hook Form holds answers in memory while the page is open; localStorage stores only the journey token after profile submission and reads it before submission. There is no draft endpoint, draft ID, snapshot-at-start, active-question list, or resume cursor. A participant leaving/reloading before submission should not be described as supported save/resume.

Proposed: when an integrated attempt starts, freeze all configuration and content inputs. If the church changes toggles later, the in-progress attempt continues against its frozen active list; new attempts use the new configuration. Do not silently add/remove questions, reinterpret saved answers, or recalculate prior progress. If a frozen question is retired, preserve it as a historical inactive row with its answer and show a clear migration/error policy rather than guessing. On resume, validate the attempt version and return to the saved round/question cursor.
