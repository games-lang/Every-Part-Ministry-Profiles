## 1. FAIL — Onboarding never asks for the leader's name or contact email
**File:** `artifacts/every-part/src/pages/church-onboarding.tsx`, plus the server-side church-creation path (`artifacts/api-server`, `lib/db` — search for where the defaults are seeded)
**Observed:** A brand-new account walks a 3-step onboarding (Welcome/church name → Tradition → Gift starting point). It never asks for the leader's name or contact email, so there is no email validation to test. The new church is then seeded with fake defaults: Administrator Name = "Church Administrator", Contact Email = "admin@example.com", and the dashboard greets "Welcome back, Church Administrator". The profile slug is a generic `your-church-xxxxxxxxxx`, not derived from the church name.
**Fix:**
- Add leader name and contact email fields to onboarding with real validation (required, valid email format, clear inline errors).
- Use the entered name/email as the church's administrator name and contact email — never seed "Church Administrator" / "admin@example.com".
- Derive the profile slug from the church name (slugified, with a short random suffix only on collision), e.g. "TEST Church" → `test-church-xxxx`.

## 6. FAIL — Concatenated accessible names (expanded list)
**Observed in the live app's accessibility tree:** "8sectionsenabled", "Current code:Not set", "1member" / "0members", "1personadded" / "0peopleadded", "©2026Every Part".
**Notes:** The page *visually* renders spaces — the bug is that the accessibility tree exposes the concatenated form. Adjacent JSX expressions with only JSX whitespace between them are unreliable here.
**Fix:** Compose each of these as a single JavaScript string (e.g. `` `${count} ${word}` ``) instead of adjacent JSX expressions, so the accessible name can never collapse. Known locations:

- Then audit the whole frontend for the same pattern (a value directly abutting a word with only JSX whitespace between) and fix every occurrence.
